# Turnstile — Kanboard のログインフォームに Cloudflare Turnstile を

[English](README.md) · [繁體中文](README.zh-TW.md) · **日本語**

サインインボタンの真上に [Cloudflare Turnstile](https://developers.cloudflare.com/turnstile/)
のチャレンジを置き、**ユーザー名とパスワードを見る前に**サーバー側で検証します。

Kanboard には元から CAPTCHA がありますが、数回ログインに失敗して初めて出てくるうえ、
GD で描かれた画像なので OCR に難なく読まれます。Turnstile なら毎回のログインで動き、
ほとんどの訪問者には見えず、しかもセッション内の値ではなく Cloudflare に問い合わせて
確かめます。

コアのファイルは書き換えず、テンプレートも上書きせず、テーマも必要ありません。素の
Kanboard でそのまま正しく表示されます。

---

## インストール

Kanboard のプラグインは `plugins/` 直下のディレクトリで、その名前がそのまま名前空間に
なります。つまりどの方法で入れるにせよ、置き場所は `plugins/Turnstile` です。

**git から:**

```
cd /path/to/kanboard/plugins
git clone https://github.com/kaiyichen0421/kanboard-cloudflare.git Turnstile
```

**zip から** — シェルの使えないホスト向けに:

```
unzip Turnstile-x.y.z.zip -d /path/to/kanboard/plugins
```

アーカイブには `Turnstile/` ディレクトリごと入っているので、`plugins/` に展開するだけで
収まります。`PLUGIN_INSTALLER` が有効なインスタンスなら、同じファイルを
**設定 → プラグイン → URL からインストール** でもそのまま使えます。

あとはページを再読み込みするだけです。クリアすべきキャッシュも、走らせるマイグレーションも
ありません。テーブルは一つも作らず、Kanboard 自身の `settings` に 2 行書くだけです。

アンインストールはディレクトリを削除するだけ。残るのはその 2 行だけで、プラグインが
なければ何の働きもしません。

### 必要なもの

Kanboard 1.2.0 以降と、サーバーから `challenges.cloudflare.com` への外向き HTTPS。検証は
サーバー間の通信なので、送信をフィルタしている環境ではこのホストを許可してください。
許可されていなければ、すべてのログインが閉じる側に倒れます。

## 設定

**1. ウィジェットを作る。** Cloudflare のダッシュボードで **Turnstile → Add widget**。
ログインページを配信するホスト名をすべて登録します。リストにないホスト名はエラー
`110200` で拒否され、しかも登録できるのはホスト名だけで IP アドレスは扱えないため、
`127.0.0.1` が許可されることはありません。開発用インスタンスには `localhost` を追加して
ください。

**2. キーを貼る。** **設定 → Turnstile 認証**（管理者のみ）。サイトキーとシークレット
キーを入力して**保存**します。

**3. 信じる前に確かめる。** **接続をテスト** は、ログインフォームには一切触れずに、保存済み
のシークレットが使えるかどうかを Cloudflare に尋ねます。

| 応答 | 意味 |
|---|---|
| シークレットキーは有効です。 | Cloudflare がこのシークレットを認識しました。 |
| Cloudflare がこのシークレットキーを拒否しました。 | シークレットが違うか、削除済みのウィジェットのものです。 |
| Cloudflare に接続できませんでした: … | サーバーから `challenges.cloudflare.com` に到達できません。 |

`siteverify` には疎通確認用のエンドポイントがないので、ここではわざと無効なトークンを
送っています。シークレットが正しければ `invalid-input-response`、壊れていれば
`invalid-input-secret` が返る——この 2 つを区別することが目的です。「届かない」と
「拒否された」では直すものが違います。

**両方の欄を空にすれば無効になります。** ウィジェットは描画されず、バリデータはそのまま
通し、Content-Security-Policy も広げません。インストール直後もこの状態なので、入れただけで
誰かを締め出してしまうことはありません。

### 締め出されてしまったら

この検査は設計として閉じる側に倒れます。キーを設定したあとは、Cloudflare が明確に認めない
ログインは通りません。ウィジェットを消した、キーに余分な空白が混じった、ホスト名をリストに
入れ忘れた——どれも管理者を含む**全員**を締め出します。

戻る道は、同じ 2 行を消すことです。

```sql
DELETE FROM settings WHERE option IN ('turnstile_site_key', 'turnstile_secret_key');
```

データベースクライアントが手元になければ、`plugins/Turnstile/` を削除しても構いません。
どちらでも、次のリクエストから元のログインフォームに戻ります。

どの失敗だったかはブラウザが教えてくれます。Cloudflare 自身は「Troubleshoot」というリンクを
出すだけで何も語らないので、このプラグインはウィジェットの下にコードを表示します。`110200`
はホスト名がリストにない、`400xxx` はサイトキーが無効、`300xxx` はチャレンジの実行失敗、
`600xxx` はタイムアウトです。

## しくみ

### 門

チャレンジは認証情報より先に検査されなければならず、Kanboard がそのために走らせる列は
`AuthValidator::validateForm()` ただ一つです。`Plugin.php` はコンテナの `authValidator`
サービスを差し替え、その列に一段だけ差し込みます。

```php
array('validateFields', 'validateLocking', 'validateCaptcha', 'validateTurnstile', 'validateCredentials')
```

この位置から二つのことが決まります。チャレンジに失敗したリクエストはパスワードの検査まで
辿り着かないので、ウィジェットを飛ばして `/login/check` に直接 POST しても拒否されます。
このトークンは任意の項目ではなく、バリデータそのものです。そして `validateLocking` の
**後**、`validateCredentials` の**前**にあるため、チャレンジの失敗は Kanboard の
ブルートフォース対策のカウントを進めることも、リセットすることもありません。

Cloudflare が `"success": true` を返さない限り、そのログインは通りません。そもそも
リクエストを送れなかった場合も同じです。利用者に見えるのは
「認証に失敗しました。もう一度お試しください。」の一行だけで、理由は Cloudflare の
エラーコードとともに、ブラウザではなく Kanboard のログに記録されます。

### ウィジェットの置き場所

Kanboard のログインテンプレートが用意しているフックは二つ、フォーム全体の上と `</form>`
の後。どちらもフォームの中ではありません。そしてフォームの外に描かれたウィジェットは、
Turnstile が自分で作るトークンの入力欄もフォームの外に置くので、ブラウザはそれを送信して
くれません。

そこでプラグインは 2 番目のフックに空のプレースホルダだけを出し、
`Assets/js/turnstile.js` がそれをフォームのアクション領域の先頭へ——つまりサインイン
ボタンのすぐ上へ——移します。Turnstile はフォームの内側に描かれ、そのトークン欄は
ユーザー名やパスワードと一緒に、ごく普通の input として送信されます。値をコピーする処理も、
隠しフィールドを維持する仕組みも要りません。

アクション領域の「前」ではなく「中」なのには理由があります。テーマは flexbox と明示的な
`order` でこのフォームを組み替えて構いません——「ログイン状態を保存する」と
「パスワードをお忘れですか？」を一行に並べる方法は、Kanboard の素のマークアップでは他に
ないからです——そしてその `order` の値こそ、このプラグインには推測できないものです。
ボタンを収めた箱の中にいれば、ボタンがどこへ動いてもウィジェットは付いていきます。

### api.js をテンプレートではなくスクリプトが読み込む理由

ウィジェットは explicit render で描画し、`api.js` はテンプレートの `<script>` タグでは
なくプラグイン自身のスクリプトが要求します。読み込み順を運任せにせず、決めてしまうためです。

普通のやり方——要素に `cf-turnstile` を付け、`data-callback` にコールバック名を書く——では、
その名前は `api.js` が動いた時点で `window` から探されます。Kanboard はプラグインの
スクリプトを `defer` で読み込み、`api.js` は `async` になるので、`api.js` の方が先に着いて
コールバックを見つけられず、黙って捨てることがあります。症状は最も厄介な種類です。
ウィジェットは **成功!** と表示しているのに、ログインは「トークンがない」として拒否される。
このスクリプトが動き終えてから `api.js` を読み込み、`render()` には本物の関数参照を渡す。
そうすればこの事故は起こりようがありません。

インラインではなくファイルなのも好みの問題ではありません。Kanboard は
`default-src 'self'` を送るので、インラインスクリプトは拒否されます。

### Content-Security-Policy

Kanboard の既定のポリシーは外部由来のものを一切許可しないため、
`challenges.cloudflare.com` を `script-src` と `frame-src` に加えます。ただし、サイトキーが
実際に保存されているときだけです。入れただけで設定していないプラグインは、ポリシーを
一文字も変えません。

### ライトとダーク

ウィジェットは `theme: 'auto'` で描画され、OS の設定に従います。Kanboard 自身のライト /
ダークは利用者ごとの設定で、ログインフォームはまだ利用者がいない唯一の画面なので、他に
従うものがありません。
